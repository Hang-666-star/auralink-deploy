# AuraLink 四仓库协作与发布

## 职责与分支

| 仓库 | 职责 | 日常集成 | 阶段发布 |
| --- | --- | --- | --- |
| `auralink-web` | 前端页面与交互 | 功能分支 → PR → `main` | `main` → PR → `release` |
| `auralink-core-api` | Core API、业务逻辑与目录数据接口 | 功能分支 → PR → `main` | `main` → PR → `release` |
| `auralink-ai-service` | AI 服务代码与服务契约 | 功能分支 → PR → `main` | `main` → PR → `release` |
| `auralink-deploy` | 部署配置、版本记录与发布流程 | 功能分支 → PR → `main` | `main` → PR → `release` |

每个仓库有独立的本地目录、Git 历史及 `origin`。同事在自己的功能分支工作，通过 PR 把已验证成果汇入 `main`。`main` 是协作集成点；`release` 表示已选定的阶段版本。四仓库采用相同分支模式，不要求搬进一个仓库。

上表是四仓库共同采用的目标流程。是否已经强制执行，必须以各仓库实际分支、ruleset、状态检查、部署环境和成功运行记录为准。添加文件不会自动创建远端分支、配置规则或接通生产部署。

## 从需求到合并

1. 认领任务，说明涉及哪个仓库及接口依赖。需要跨仓库修改时互相链接 PR。
2. 从对应仓库最新 `main` 创建功能分支；运行该仓库自己的检查。
3. 向 `main` 提 PR，写明具体行为变化和验证证据。界面变化附截图，接口变化说明兼容性。
4. 负责人审核、必需 CI 通过后合并。`CODEOWNERS` 必须配合规则设置才能要求负责人审核。
5. 阶段成果准备好后，提交同仓库 `main` 到 `release` 的 PR。来源检查应同时验证分支名和来源仓库。

CI 验证与部署授权是两个环节：允许同事提交代码不等于允许任意代码直接进入生产。对 `main`、`release` 禁止直接推送和强制推送，并设置必需审核与检查；生产环境审批按实际团队安排配置。不同仓库的 workflow 名称与所需工具可以不同。

## 记录跨组件版本

前端与后端独立合并、独立触发 Actions，并不构成一次原子发布。每次生产发布都应在发布 PR 或后续采用的版本记录文件里填写实际值，至少包含：

| 字段 | 记录要求 |
| --- | --- |
| 发布编号与时间 | 可关联到本次发布的唯一标识和实际时间 |
| 各组件目标版本 | 四仓库完整提交 SHA；没有变更的组件注明继续使用的已部署 SHA |
| 构建与验证 | 相关 Actions 链接、构建产物标识及实际通过的检查 |
| 当前运行版本 | 从服务器或发布记录核实的部署前版本；未知时明确写“待核实” |
| 发布顺序 | 依据接口兼容要求决定，不能默认四仓库可任意顺序部署 |
| 数据变更 | 是否涉及数据库迁移或画作导入，单独列出步骤、验证和恢复依据 |
| 验收与恢复 | 组件健康检查、关键用户路径及上一可用版本的恢复入口 |

不要使用 `latest` 标签代替可追溯版本；若采用镜像，还应记录镜像 digest。不要把目标 SHA 写成已部署 SHA。合并成功、CI 成功和生产验收成功分别记录。

接口变更优先保持旧前端和旧后端的短期兼容；无法兼容时，在发布 PR 中明确协调步骤及验证窗口。数据导入属于独立的数据操作，不能因为代码合并到 `release` 就默认执行或认定完成。

## 本仓库与 R25 的接通边界

本仓库现有 Compose/Nginx 配置描述的是旧 Docker 架构，包含 SQLite Core API；现有 R25 生产采用 PostgreSQL 及另一套运行方式。当前新增 `Deployment configuration CI` 只验证旧模板，未增加生产部署 workflow。合并本仓库 `release` 不应被描述成服务器已更新。

后续接通 R25 发布时，需要先完成以下实际工作：

- 核对服务器中各组件运行目录、部署来源、启动方式、端口及当前版本，形成经核实的映射。
- 核对 Web 和 Core API 已有发布 workflow、候选验证、生产审批与恢复入口；在它们的实际能力上衔接，避免重复发布同一组件。
- 明确 AI Service 的运行依赖、模型位置、资源需求及验收方法，再接入对应组件更新流程。
- 明确 Deploy 仓库最终保存什么经过核实的配置或版本记录，并确定谁负责触发发布；在完成这些决定前不编造生产 manifest。
- 使用组件级更新方式，明确失败时如何保留或恢复上一可用版本。验证不会误停无关组件，不会修改数据库、画作和模型文件。
- 做一次有真实记录的发布验收：目标 SHA、实际部署 SHA、Actions 结果、组件健康检查和用户路径结果一致，再把该路径记为“已接通”。

服务器环境变量、密钥、数据库、画作图片和模型权重保存在各自的运行或数据管理位置。协作仓库保存代码、示例配置和流程证据；实际凭据通过受控的部署环境提供。
